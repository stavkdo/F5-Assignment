Question

I need further explanation on these functions: _redact_string, rule.pattern.sub

_redact_string takes one string, runs every value rule over it in config order, and returns the string with each match replaced.

def _redact_string(self, text: str) -> str:
    for rule in self.rules.value_rules:
        text = rule.pattern.sub(lambda m, rule=rule: self._replace_match(rule, m.group(0)), text)
    return text

What pattern.sub does

rule.pattern is a regex compiled once at startup. .sub(repl, text) finds every non-overlapping match, left to right, and returns a new string with each one replaced (strings are immutable, hence text = …). When repl is a function, sub calls it once per match with a Match object and puts its return value in place of the match. A fixed string can't run a validator, count, or choose an action, so we need the function form.

p = re.compile(r"\d+")
p.sub("#", "a1b22")                          # "a#b#"
p.sub(lambda m: f"<{m.group(0)}>", "a1b22")  # "a<1>b<22>"

The lambda

m is the match, m.group(0) its text. rule=rule freezes the current loop's rule into the lambda, guarding against Python's late binding (a lambda looks variables up when it runs, not when it's made):

[f() for f in [lambda: n for n in range(3)]]      # [2, 2, 2]
[g() for g in [lambda n=n: n for n in range(3)]]  # [0, 1, 2]

Here sub calls the lambda immediately in the same iteration, so the bug couldn't happen anyway. The default argument is defensive, and knowing that shows you understand it.

_replace_match: the decision for one match

If the rule has a validator and it rejects the text, return the text unchanged: sub puts the same text back and nothing is counted. Otherwise count it under the rule's name and return the action's result.

Note

Check what NDJSON is.

Newline-Delimited JSON, also known as JSON Lines (.jsonl): a text file where every line is one complete JSON value, separated by \n.

  • Each line must be valid JSON on its own, and a value can't span lines. A newline inside a string is written as the escape \n, which is how line 9's multi-line ticket fits on one line.
  • UTF-8, and \r\n is tolerated.
  • A parser may skip empty lines but must document it, which bears on your phase 3a decision about lines 19 and 22.

Logs use it instead of one big JSON array because it can be processed a line at a time (that's what makes streaming possible), appended to, and one corrupt line doesn't spoil the rest. A [...] array has to be read to the end before it's valid.

Your idea

I think the best way to solve the cards with spaces/dashes is to change the regex.

Agreed, and done

The pattern lives in rules.yaml, so that's the right place to fix it, and luhn already ignores spaces and dashes. The catch is how to change it. The obvious version has a trap:

# naive: "digits with optional separators"
\b(?:\d[ -]?){12,18}\d\b

# on this text:  id 1 4111 1111 1111 1111
# the match starts at the lone "1":  "1 4111 1111 1111 1111" (17 digits)
# Luhn rejects it -> the text is left as-is -> the real card leaks

Why it leaks: re.sub finds a match first and asks the validator afterwards. When the validator says no, the regex engine doesn't go back and try a shorter match: the backtracking is over by then. So the pattern itself has to avoid swallowing neighbours. The fix lists the layouts cards are actually printed in:

\b(?:\d{13,19}                              # all together
   |\d{4}([ -])\d{4}\1\d{4}\1\d{4}           # 4-4-4-4  Visa, Mastercard, Discover
   |\d{4}([ -])\d{6}\2\d{4,5})\b             # 4-6-5 Amex, 4-6-4 Diners

([ -]) captures the first separator, and \1 means "the same character again". That's a back-reference, so 4111 1111-1111 1111 with mixed separators is not glued into one number. Detail: back-references go beyond regular languages, which is exactly why Go's RE2 engine doesn't support them. In Go the "same separator" check would move into the validator.

Cost: mixed separators and 19-digit cards printed in groups aren't matched. Both are in the known gaps.

Your answer

How do you avoid leaking data in error messages? — "State only the error and the line it happened in."

Correct

Three details make it hold in code:

  • A fixed set of reasons, never str(exception). Python's messages can quote the input: UnicodeDecodeError says 'utf-8' codec can't decode byte 0xff in position 3. The five reasons are constants: invalid JSON, not a JSON object, nesting too deep, line too long, internal error.
  • No tracebacks. A bug in one line (any unexpected exception) becomes an internal error record, and the stream continues. Locals in a traceback could hold the line.
  • Counts are transactional. Redactions are counted in a per-line Counter and merged only when the line succeeds, like a database transaction that commits or rolls back.

Tested: test_failures.py feeds lines containing erin@example.com and checks that it appears in neither stdout nor stderr, including a fake bug whose exception message contains the line.

Your answer

How deep do you decode nested encodings, and why stop there? — "I don't know, but shouldn't we try the most we can?"

Not quite

Decoding everything sounds safe but makes things worse:

  • Cost an attacker controls. Every level is another full parse, and the sender decides how many levels there are. Unbounded decoding is a denial-of-service lever. Compressed formats can be a decompression bomb (a few KB that expand to GBs).
  • False positives. Almost any token "is" valid base64. Decoding guesses would turn random IDs into garbage and redact by accident.
  • Round trips. Whatever we decode, we must re-encode exactly, or idempotency breaks.

What the redactor does: it decodes only formats that announce themselves and round-trip without loss (JSON in a string, form encoding, URL queries), up to 3 levels. Past that it fails closed.

A real finding along the way: the first version just stopped at 3 and treated the rest as free text. The test for it failed, because 5 levels deep the quotes are escaped (\"password\"), so even the key=value scan can't see the key, and deep-secret leaked. Now, if there's still JSON past the limit, the line becomes an error record. The same test also showed that double-encoded JSON (a JSON string holding JSON) wasn't decoded at all, which is common in real logs. Fixed too.

One sentence: "Three levels of self-describing, lossless encodings, because each level costs a parse the sender controls, and beyond that the line is refused rather than passed through unread."

Your answer

Plain SHA-256 of a card number or email: is it really safe? — "From what I know you can't go back from SHA-256, so it's safe."

Half right

"Can't go back" is preimage resistance, and it's true. But nobody needs to go back: they can guess forwards. Hash every possible input and compare. That's only infeasible when the input space is huge, and here it isn't:

Card digitsUnknown?
First 6 (bank BIN)public, a few thousand common values
Last 4often known: partial prints them in the same log
Last digitthe Luhn check digit, computed from the others
Leftabout 5 digits = 100,000 guesses, under a second even in plain Python

Emails are similar: billions of leaked addresses are public, and for one target you guess first.last@company.com. In CS terms, a one-way function doesn't hide a value with little entropy.

The fix is a keyed hash, HMAC-SHA256(secret, value). Same input still gives the same output, so analysts can still correlate, but without the key you can't test guesses. Per your decision (the brief asks for SHA-256), the code keeps plain SHA-256 and the README explains this.

A false positive is harmless text the rule redacts anyway. A false negative is real PII it misses. Tuning a regex trades one against the other: precision versus recall. Cards have a built-in filter (Luhn rejects ~90% of random numbers), but SSNs and phones don't.

Question

Can you explain further the decisions you made, and why?

Four decisions were mine, not yours. All four come from the same question: when the redactor isn't sure, does it lean towards leaking or towards over-redacting? For secrets it leans towards over-redacting, except where that would quietly damage data that isn't secret.

1. Every field is checked (default deny)

Phase 2 used an allow-list of fields to redact (headers, body) and passed everything else through. Now it's the reverse: headers uses headers rules, and every other field, path, ts, method and fields nobody expected, is checked with body rules.

Why: Phase 2 leaked line 30's ?token=…&email=… because path was on the pass-through side. A new field from some upstream service ("query", "cookies", "user") would leak silently too. In security this principle is called fail-safe defaults: anything not explicitly known to be safe is treated as unsafe. Cost: a little CPU on ts and method, where nothing ever matches. Bonus: no special path code was needed; the URL handling for any string covers it. Test: test_unknown_top_level_fields_are_redacted_too.

2. Value rules also check key names

Key names go through the value rules: {"bob@example.com": {...}} → {"sha256:5ff8…": {...}}.

Why: maps keyed by an identifier are common (per-user settings, a cache keyed by email). The brief says "redact anywhere", and a key is part of the data. Key rules still match the original name, so password is still recognised. Cost: V regex scans per key. If two keys redact to the same text (two masked ones) they'd collide, which the duplicate-key support from 3b handles. Test: test_value_rules_also_apply_to_key_names.

3. In free text, a key rule applies whatever its scope

auth-headers has scope: headers. Inside a JSON body it doesn't fire. But inside free text it does: "error: Authorization: Bearer abc failed" → "error: Authorization: **** failed".

Why: a scope describes where a key sits in the structure. Free text has no structure: a body that's a pasted raw HTTP request or a debug log contains header lines, and we can't know where they came from. If scope applied, that bearer token would leak. The two errors don't cost the same: over-masking a word in a log line versus leaking a credential. Cost: false positives like secret: santa → secret: ****. Only names that are already sensitive key names are affected. Test: test_key_value_pairs_in_free_text.

4. JSON numbers are never checked by value rules

Value rules (email, card, SSN…) read strings only. A bare number like "ts_us": 1705312800123456 is never checked. Numbers are still redacted by key rules: "card_number": 4111111111111111 → "************1111".

Why: (1) the brief defines value rules as matching "the content of any string value". (2) Luhn passes 1 in 10 random numbers, so about 1 in 10 sixteen-digit IDs or microsecond timestamps would be turned into the string "************3456". That's a type change that breaks downstream schemas, and it happens at random. Line 35's timestamp only survives because it happens to fail Luhn. Cost: a card stored as a bare number under a harmless key ("amount": 4111111111111111) stays. That's a known gap with a strict xfail test, and the README says so.

Why the email regex was O(n²)

To find the leftmost match, re tries start position 0, 1, 2… On a run of n letters with no @ (a base64 upload), from start i the part [A-Za-z0-9._%+-]+ takes the remaining n−i letters, finds no @, and gives them back one at a time looking for one. That's about n−i steps per start, and n + (n−1) + … + 1 = n(n+1)/2 in total. Measured: 5 KB → 44 ms, 10 KB → 183 ms, 20 KB → 715 ms. Each doubling quadruples the time.

The lookbehind (?<![A-Za-z0-9._%+-]) fails in O(1) at every position inside a run, so only each run's first character does the scan: O(n) in total, and 1 MB in 16 ms. The matches are identical, because the leftmost match always starts at the beginning of a run.

Can it be less? Not below O(n): a correct detector must read every character, since any unread one could be the @. That makes Ω(n) a lower bound, and the fix reaches it. Only the constant can shrink: a possessive […]++ skips the give-back walk, but on its own (without the lookbehind) it would still be O(n²). In the README: yes, now as its own section, Regexes are part of the time complexity, with the measurements, the proof that the matches are the same, and the lower bound.

The lookbehind (?<![A-Za-z0-9_-]) means "an eyJ counts only if the character before it is not a base64url character", so a token may start only at the beginning of a run. That is what makes the rule linear: inside eyJeyJeyJ… every eyJ after the first has a J before it and is skipped in O(1).

Why the email rule lost nothing with the same trick: every character of a run can be part of an address, so the leftmost match always starts at the run's beginning anyway. Why the JWT rule does lose something: a JWT starts with fixed text, eyJ, which can sit in the middle of a run. Life of one line

What happens to each line, in order

  1. redact_stream cli.py

    Takes the next line from the file or stdin. Looping over a Python file object reads one line at a time, so memory doesn't grow with the file.

  2. redact_line → json.loads

    Parses the line. A parse failure becomes LineError("invalid JSON"); valid JSON that isn't an object becomes LineError("not a JSON object").

  3. redact_record → _redact_message

    Runs once for the top level and once for response. Only headers and body are touched, and the field name becomes the rule scope.

  4. _walk

    Dispatches on type: dict → _walk_dict, list → each item, string → _redact_string, numbers, booleans and null are returned unchanged.

  5. _walk_dict → _key_rule_for

    For every key, finds the first key rule that matches in this scope. No match: recurse into the value. remove: drop the key. Anything else: apply the action to the whole value and skip value rules for it.

  6. _redact_string → _replace_match

    Each value rule runs pattern.sub over the string, in config order. For every match the validator (if any) decides, then the match is counted and replaced.

  7. json.dumps

    Serialises back to one compact line (separators=(",", ":"), ensure_ascii=False) and writes it to stdout.

  8. format_summary

    After the last line: lines read, written and skipped, plus the count for every rule (zeros included), on stderr.

def _walk(self, value, scope: str):
    if isinstance(value, dict):
        return self._walk_dict(value, scope)
    if isinstance(value, list):
        return [self._walk(item, scope) for item in value]
    if isinstance(value, str):
        return self._redact_string(value)
    return value  # numbers, booleans, null

def _walk_dict(self, obj: dict, scope: str) -> dict:
    out = {}
    for key, value in obj.items():
        rule = self._key_rule_for(key, scope)
        if rule is None:
            out[key] = self._walk(value, scope)
        elif rule.action == "remove":
            self.counts[rule.name] += 1
        else:
            out[key] = self._apply_key_rule(rule, value)
    return out

Decisions to defend

The choices behind the code

Each one is a real decision with a cost. Some are temporary and marked with the phase where they get revisited.

Parsing and streaming

Parse each line fully

json.loads on the whole line instead of a streaming JSON tokenizer.

Why: one line is one small record, and the standard library parser is simple and correct. Cost: one enormous line is loaded whole. There is no maximum line size yet.

Line-by-line loop

for line in f over the file or stdin; one line in memory at a time.

Why: memory depends on the longest line, not on the file size, which is what "inputs far larger than memory" needs.

Force UTF-8

stdin and stdout are reconfigured to UTF-8 with \n line endings.

Why: Windows defaults to cp1252, which would mangle 名前, Hebrew and emoji. Cost: invalid bytes become U+FFFD without a warning.

Rule semantics

Scope = field name

headers and body are redacted, in the request and in response. ts, method, path and status are passed through.

Why: the same function serves both directions of the transaction. Cost: secrets in the URL query string leak (line 30).

Key rule beats value rules

If a key rule matches, its action covers the whole value and value rules are skipped for it.

Why: the field name is the stronger signal, and it avoids redacting and counting the same secret twice. Example: X-Api-Key: sk_live_abc123 is hashed by api-key-names; api-key-prefix never sees it.

Config order

The first matching key rule wins. Value rules run one after another, each on the previous one's output.

Why: predictable, and the YAML author controls priority. Cost: one rule's replacement can affect what a later rule sees.

Case-insensitive names

exact lists are compared lower-cased. Regex rules use search with the YAML's own anchors and flags.

Why: HTTP header names are case-insensitive (RFC 9110), so AUTHORIZATION on line 14 must be caught.

Validators at load

validator: luhn is resolved to the function when the rules load. A match that fails it is left untouched and not counted.

Why: an unknown validator fails at startup, not on line 40,000.

Short partial values

partial on a value of 4 characters or fewer hides all of it.

Why: "keep the last 4" on "1234" (line 38) would print the whole value.

Non-string values

Under a key rule, null and booleans are kept; numbers, lists and objects are redacted as their JSON text.

Temporary. Good enough for the happy path; revisited in phase 3b.

Safety

Fail at startup

Any config problem raises RulesError: exit code 2, nothing on stdout. 11 kinds of broken config are tested.

Why: fail closed. The service will need exactly the same behaviour.

Errors without content

Bad lines are skipped and reported as line 20: skipped: invalid JSON. Messages are fixed strings written in our code, never copied from the parser.

Why: the parser's own messages could include data. Cost: skipped lines are lost; the final policy is a phase 3a decision.

Input is not mutated

The walker builds new dicts and lists instead of editing the parsed record.

Why: easier to test and safe if a caller still holds the original.

Structure

Stream function

redact_stream(redactor, lines, out, err) is separate from main.

Why: tests drive it with StringIO, and the HTTP service can drive it with request streams.

Counts by rule name

A Counter keyed by rule name. Duplicate rule names are rejected at load so counts can't merge.

One dependency

PyYAML at runtime, because the standard library has no YAML parser. pytest only for development.

MemoryO(L + D)

L is the longest line, D the nesting depth (call stack). Independent of file size.

TimeO(B × V)

B input bytes, V value rules: every string is scanned once per value rule, every key checked against the key rules.

Life of one line, Phase 3

From bytes in to bytes out

  1. read_lines stream.py

    readline(max + 1) on the binary stream. Longer than the cap: the rest is read in 64 KiB chunks and discarded, and the result is line too long.

  2. _decode

    Strict UTF-8. Invalid bytes become U+FFFD with a warning on stderr. A byte-order mark on line 1 is dropped. A blank line is skipped and counted.

  3. redact_line → jsonio.loads

    Numbers stay as their text, repeated keys are kept, NaN is rejected. Failures raise LineError with one fixed reason.

  4. redact_record → _redact_message

    A fresh per-line counter. headers uses the headers scope, response is handled the same way, and every other field uses the body scope (default deny).

  5. _redact_pair

    First matching key rule wins. remove drops the key; other actions go to _apply_key_rule, which redacts every scalar and keeps the shape. The key's own text goes through value rules too.

  6. _walk

    Same recursion as Phase 2, plus a depth counter: past 100 levels the line is refused.

  7. _redact_string

    JSON inside? Parse and walk it. A URL with a query, or a form body? Per pair. Otherwise free text: key=value pairs, then the value rules.

  8. jsonio.dumps

    Compact, key order and number text kept. A lone surrogate switches that line to \u escapes.

  9. counts.update · error record

    The line's counts are merged only on success. Any LineError, or any unexpected exception, becomes a {"redactor_error":…} line plus one stderr line.

Decoding depth: 3

JSON in a string, form encoding and URL queries, nested up to 3 levels. Past that, if there is still JSON inside, the line is refused.

Found by a test: the first version treated level 4+ as free text. But there the quotes are escaped (\"password\"), so the key=value scan saw nothing and the secret leaked. The same test revealed that double-encoded JSON (a JSON string holding JSON) wasn't decoded at all.

Free text ignores scope

Authorization: Bearer abc pasted into a body becomes Authorization: ****, although auth-headers has scope headers.

Why: in free text we can't tell where a pair came from, so we over-redact. Cost: a bare value stops at whitespace, so password=correct horse only masks correct.

Decoded = body scope

A header holding {"password":"x"} gets secret-fields (scope body) applied.

Why: the keys inside are payload, not header names.

Bug found later

In https://x/r?token=abc inside a sentence, the scan read https as a key and the rest as its value. That consumed the text, so the sensitive token= was never seen.

Fix: keys and values are matched by two patterns, and a value is only read after a sensitive key. Still a single O(n) pass, timed on 400 KB of a:a:a:….

Default deny

path, ts and unknown top-level fields are walked as body.

Why: a field nobody listed shouldn't be passed through. That's how the query string on line 30 gets redacted with no special code for path.

Not decoded

base64, HTML entities, gzip.

Why: they don't announce themselves (almost any token is valid base64), and compressed input can be a decompression bomb. Listed as known gaps.

Grouped layouts

4-4-4-4, 4-6-5, 4-6-4, with one separator throughout (back-reference \1).

Why not "digits with optional separators": on id 1 4111 1111 1111 1111 it starts at the lone 1, fails Luhn, and sub doesn't retry a shorter match, so the card leaks. Tested.

Numbers kept as text

Why: a redactor should change secrets, not amounts, and anyone diffing logs would see 10.50 → 10.5 as a change.

An integer literal goes through the value rules as its digits: "amount": 4111111111111111 → "************1111". Numbers that aren't redacted keep their type and text. Signed, fractional and exponent numbers are skipped.

3e · idempotency

f(f(x)) = f(x)

CS idea: every value the redactor writes must be a fixed point of the redactor. mask("****") = "****" and partial("****1111") = "****1111" already are. hash isn't: sha256(sha256(x)) ≠ sha256(x).

Recognisable hashes

Hashes are written sha256:<64 hex>. A hash rule leaves such a value alone, and the mask string too (line 12's "X-Api-Key":"****" stays **** instead of becoming the hash of four stars).

Why not "any 64-hex string": a real API key can be 64 hex characters. Skipping it would leak it. The prefix is something a real secret practically never looks like.

Rewrite only on change

Embedded JSON and form pairs are re-encoded only if a redaction happened inside (the per-line counter moved).

Why: untouched data keeps its exact bytes, and our own compact output reads back to the same text.

Decisions to defend · TASKS.md Phase 3

One sentence each

Bad line output

An error record with the line number and a fixed reason: it can't leak, keeps the output valid NDJSON, and makes the loss visible instead of silent.

No leaks in errors

Reasons come from a fixed vocabulary of five strings, never from an exception message, and no traceback is ever printed.

Decode depth

Three levels of self-describing, lossless encodings (JSON, form, URL query), because each level costs a parse the sender controls. Beyond that the line is refused rather than passed through unread.

Plain SHA-256

Not safe for small input spaces like cards and emails, which can be brute-forced forwards. HMAC with a secret key fixes that. The brief specifies SHA-256, so it stays, and the README explains this.

Complexity

Memory O(L) for the longest allowed line, time O(B × V), measured flat at 14–16 KiB from 10k to 100k lines.

Life of one request

From the first chunk to the last line

  1. uvicorn

    Accepts the connection and parses HTTP, including Transfer-Encoding: chunked bodies. It calls the app with receive (body chunks come from here) and send.

  2. redact() service.py

    Returns a BodyStreamingResponse right away. Its body is the async generator _redact_body, which hasn't run yet.

  3. _redact_body

    Creates this request's own Redactor and LineProcessor. The compiled rules are shared, because they never change.

  4. split_lines

    For each chunk from request.stream(): append it to the unfinished line, cut at every \n, and yield the complete lines as one batch. A line over 1 MiB becomes None and its bytes are dropped as they arrive.

  5. await asyncio.to_thread(_process_batch)

    The CPU work runs in a worker thread, and the event loop is free meanwhile. Each line goes through LineProcessor.process, the same code the CLI runs.

  6. yield

    The batch's output goes out as one HTTP chunk. If the client reads slowly, send waits, so we stop reading its body. That's backpressure, and memory stays at one line plus one chunk.

  7. finally

    The per-request summary goes to stderr (kubectl logs), even if the client disconnected.

asyncio, in OS terms

One event loop, and why the redaction leaves it

An event loop is cooperative multitasking in one thread. Each request is a coroutine. At every await (waiting for the network), it yields the CPU and the loop runs another coroutine. That's great for waiting, and bad for computing: a coroutine that computes for 2 s without an await holds the only thread for 2 s, so every other request, and /healthz, waits too.

asyncio.to_thread(f, batch) runs f in a pool thread and gives back an awaitable. The coroutine waits there like it would for the network, and the loop keeps serving. The GIL still lets only one thread run Python at a time, but it switches every 5 ms, so the loop gets its turns. Threads buy responsiveness, not speed; more speed comes from more pods.

Measured: 4 clients each sending 1 MB lines/healthz response time

That's why it matters for Kubernetes: the liveness probe would see 2.5 s as "stuck" and restart a pod that is only busy.

redactor/service.py · the request body
async def _redact_body(chunks, rules, max_line_bytes):
    redactor = Redactor(rules)                 # one per request: it holds per-line counts
    processor = LineProcessor(redactor, sys.stderr)
    try:
        async for batch in split_lines(chunks, max_line_bytes):
            out = await asyncio.to_thread(_process_batch, processor, batch)
            if out:
                yield out.encode("utf-8")     # one HTTP chunk, sent now
    finally:
        print(format_summary(redactor, processor.stats), file=sys.stderr)

Order: each batch is awaited before the next is read, so output order equals input order with no extra work.

Finding

Starlette's StreamingResponse ate the request body

  • Symptom: sending the sample as one block gave 48 lines back. Uploading the same file in pieces gave back 0 lines, with status 200 and no error anywhere.
  • Cause: in Starlette 0.41, StreamingResponse.__call__ runs two tasks: one sends our body, the other (listen_for_disconnect) loops on receive() and drops every message that isn't "client disconnected". Uvicorn speaks ASGI 2.3, so that path is used. But receive() is also where body chunks come from. The listener was stealing and dropping them, and our generator waited for chunks that never came.
  • Why it hides: most endpoints read the whole body before they respond, so there's nothing left to steal. We read and respond at the same time, which is exactly what the brief asks for.
  • Fix: BodyStreamingResponse overrides __call__ to just send. A disconnect is still noticed, because our own request.stream() raises ClientDisconnect.
  • Guard: a test talks to a real uvicorn server over a raw socket. It sends a line, waits for its redacted copy, then sends the next. With Starlette's class it fails (times out in 5 s); with ours it passes.

Root cause

Two bugs in one pattern

rules.yaml · provided
pattern: 'eyJ[A-Za-z0-9+/=]+\.[A-Za-z0-9+/=]+\.[A-Za-z0-9+/=]*'

1. Wrong alphabet: the leak. A JWT is header.payload.signature, and each part is base64url (RFC 7515): A-Z a-z 0-9 - _, with no = padding, so it is safe in URLs. The class [A-Za-z0-9+/=] is plain base64. One base64url character in 32 is a - or _, so about 99% of 150-character tokens contain one. What happens next depends on where it sits:

First _ or - is in…What the regex doesResult
the signature (line 15)the last part is *, so the match just ends at the _masked up to the _; _adQssw5c leaks
the payload (lines 11, 16: eyJhIjoiPz8_In0)the second part stops at _, the required \. isn't there, and the whole match failsnothing masked, the whole token leaks

2. Quadratic time: a denial-of-service hole. It's the same shape as the email bug from Phase 3. On eyJeyJeyJ…, re tries a match at every eyJ. From each one, […]+ runs to the end of the text, finds no ., and gives the characters back one by one: n starts × O(n) = O(n²). 60 KB took 2.3 s. Fixing only the alphabet still took 2.26 s (measured), so both bugs need a fix.

The fix · only rules.yaml changed

The new pattern, part by part

rules.yaml · fixed
pattern: '(?<![A-Za-z0-9_-])eyJ[A-Za-z0-9_-]++\.[A-Za-z0-9_-]++\.[A-Za-z0-9_-]*+'
PartWhy
[A-Za-z0-9_-]The base64url alphabet, from the spec. Fixes the leak.
(?<![A-Za-z0-9_-])A lookbehind: a token may start only where a run of base64url characters starts. On eyJeyJ… only the first eyJ is tried; every other position fails this O(1) check.
++ (possessive)Once taken, characters are never given back, so a failed attempt costs one pass, not a give-back walk. Needs Python 3.11+, which pyproject.toml requires.
*+ on the last partAn unsigned token (alg: none) has an empty signature and must still be masked.

A lesson from testing: the first attempt kept +/= in the class "to be safe". That broke token=eyJ…, because with = in the class the lookbehind saw = as part of the run and refused the match. Following the spec's alphabet exactly turned out to be the safer choice.

Design choice

Why not a detector in code instead of a regex

The alternative: a Python function that finds eyJ, base64url-decodes the header and checks that it is JSON with an alg field.

ArgumentExplanation
Rules are configThe brief makes the rules config-driven, and the report is about rules.yaml. A config bug fixed in config means no engine change and no new image. A code detector would also be the one rule a user can't read or change in rules.yaml.
A miss is worse than a false maskThe decode check exists to reject look-alikes, but it would also reject a token cut short by an upstream logger or with a damaged header. That would be a leak. A false mask costs a little readability. And eyJ….….… is almost never anything but a JWT, because eyJ is {" in base64.
No speed gainBoth are one linear pass. The decoder adds a base64 decode and a JSON parse per candidate.
The trade-off

A JWT glued to a word isn't matched

The lookbehind lets a token start only at the beginning of a run. For the email rule that cost nothing: any character of a run can be part of an address, so the leftmost match always starts at the run's beginning anyway. A JWT starts with the fixed text eyJ, which can sit in the middle of a run. In jwt_eyJhbG… the _ is base64url, so the run starts at j, the eyJ has _ before it, the lookbehind refuses, and the whole token leaks.

The first option was chosen because in real traffic a JWT follows a space, a quote, =, : or Bearer , never a base64url character, and a slow regex in a service is an outage for everyone. Bonus 1 · --hmac

Why plain SHA-256 isn't enough, and what HMAC changes

SHA-256 can't be reversed, but it can be guessed forwards: anyone can compute sha256("bob@example.com") and search the logs for it. A card has only about 105 unknown candidates once its bank prefix, last 4 digits and Luhn digit are known. HMAC mixes a secret key into the hash, so without the key a guess can't be tested. The same input still gives the same output, so you can still see that two lines belong to the same user.

PowerShell
$env:REDACTOR_HMAC_KEY = python -c "import secrets; print(secrets.token_hex(32))"
python -m redactor --hmac input.ndjson
# "X-Api-Key":"hmac-sha256:f5b7a9b8…"   (plain SHA-256 would be sha256:e998…)
DecisionWhy
Opt-in with a flag, SHA-256 stays the defaultThe brief defines hash as SHA-256, so the brief's command still works with no setup. A key that just happens to be set in the environment changes nothing: only the flag switches HMAC on.
Key from an environment variableNot rules.yaml (in git, and in a ConfigMap anyone in the namespace can read), not a command-line argument (shell history, ps).
No key, or shorter than 32 bytes → exit 2Fail closed: never quietly fall back to the weaker hash. 32 bytes is the hash's own length, as RFC 2104 advises.
The key is never printedThe error says "is not set" or "is too short", never the value, and the settings field has repr=False.
Prefix hmac-sha256:Says which hash was used, and lets a second run recognise it and leave it alone (idempotency). Old sha256: values are left alone too.

In Kubernetes (explained in the README, not wired up): 1. a Secret holding the key (like a ConfigMap, but for passwords and keys: kept out of git, and access to it can be limited); 2. an env var in deployment.yaml filled from it with valueFrom: secretKeyRef; 3. --hmac in the container's args. Cost: changing the key means new hashes no longer match old ones.

Bonus 2 · --watch-rules

Hot reload for long-running streams

For tail -f app.log | redactor --watch-rules > redacted.log: change a rule without stopping the stream and losing your place.

  1. before each line stream.py

    redact_stream calls RulesWatcher.check(). If less than 2 s have passed since the last check, it returns at once: one clock read.

  2. read and compare reload.py

    Read the file and compare its SHA-256 with the content the current rules came from. Same content: done. The first comparison uses the exact bytes loaded at startup, so a change made right after startup isn't missed.

  3. validate

    parse_rules_file runs the same checks as startup. Invalid (bad YAML, no rules, unknown action), or the file is gone: keep the old rules and warn on stderr once.

  4. swap

    redactor.rules = new_rules, between two lines, so no line is redacted half old, half new. The --hmac key is applied to the new rules too.

  5. flush

    In this mode each output line is flushed right away, so whoever reads the output sees it immediately instead of waiting for a full buffer.

Why CLI only: Kubernetes updates a mounted ConfigMap's file inside a running pod by itself (within about a minute), so the same watcher could run in the service. But there a failed reload would also need to be visible from outside, on /healthz or as a metric, which is more to design and test. Until then: kubectl rollout restart.
